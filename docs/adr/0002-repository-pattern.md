# ADR 0002: Consumer-Owned Repository & Constructor DI

**Status:** Accepted

**Deciders:** Lesson 2.2 — Creating & Listing Employees

**Date:** 2026-07-24

## Context

Milestone 2 requires CRUD operations for employees. The persistence strategy must
evolve: currently using in-memory storage for rapid iteration, with PostgreSQL
planned for Milestone 5.

The design must satisfy:

1. HTTP handlers must be testable without a running database.
2. Swapping storage backends (in-memory → PostgreSQL → test doubles) must not
   require changes to business logic or HTTP layer.
3. The solution must follow idiomatic Go conventions.

## Decision

**Each business package defines its own `Store` interface.** The interface is
consumed by the HTTP handler, and concrete implementations implicitly satisfy it.

```go
// internal/employees/store.go — defined where consumed
type Store interface {
    Save(ctx context.Context, emp Employee) error
    List(ctx context.Context) ([]Employee, error)
}
```

```go
// internal/employees/handler.go — accepts the interface
type Handler struct {
    store Store
}

func NewHandler(store Store) *Handler {
    return &Handler{store: store}
}
```

```go
// internal/employees/store.go — concrete implementation
type InMemoryStore struct {
    employees []Employee
}

func NewInMemoryStore() *InMemoryStore {
    return &InMemoryStore{}
}
```

**Constructors return concrete types, accept interfaces.** `NewHandler` accepts
`Store` (interface). `NewInMemoryStore` returns `*InMemoryStore` (concrete).
This follows the Go idiom "accept interfaces, return structs."

**Dependencies are wired in `cmd/server/main.go`** (the composition root). No DI
container, no service locator, no global state.

```go
// cmd/server/main.go — composition root
empStore := employees.NewInMemoryStore()
empHandler := employees.NewHandler(empStore)
srv := server.New(cfg, empHandler)
```

## Alternatives Considered

1. **No interface, concrete store directly in handler** — rejected because it
   blocks testing with alternative implementations and forces PostgreSQL
   integration before business logic is stable.

2. **Interface defined in an infrastructure package** (`internal/store/`)
   — rejected. Interfaces belong to the consumer in Go, not the implementer.
   Defining a shared interface creates a dependency magnet and breaks package
   cohesion.

3. **DI container (wire, fx, etc.)** — rejected. Explicit wiring in `main.go`
   is simpler, more transparent, and sufficient for this project's scale. No
   framework magic to learn or debug.

4. **Skip in-memory, go straight to PostgreSQL** — rejected. PostgreSQL is
   covered in Milestone 5 as its own learning unit. The in-memory store lets
   us focus on domain logic, interfaces, and HTTP handler testing first.

5. **One global `Repository` interface with generics** — rejected. Each
   business package has different persistence needs. Premature generalization
   introduces complexity without solving a real problem.

## Trade-offs

- **Pro: Testable** — handlers can be tested with any implementation of `Store`.
- **Pro: Evolvable** — PostgreSQL adapter wraps sqlc queries in a struct
  satisfying `Store` with zero handler changes.
- **Pro: Idiomatic** — follows the Go community convention of small,
  consumer-owned interfaces.
- **Pro: Explicit** — all dependencies and their instantiation order are
  visible in `main.go`.
- **Con: Interface duplication** — each package defines its own persistence
  contract. This is by design: `employees.Store` and `products.Store` are
  different interfaces representing different business capabilities.
- **Con: No concurrency safety** — `InMemoryStore` uses an unsynchronized
  slice. A mutex will be added in Milestone 10 when goroutines are introduced.

## Consequences

- All future business packages (products, production orders, reporting) follow
  the same pattern: package-owned `Store` interface, concrete implementation,
  constructor DI in `main.go`.
- When PostgreSQL is integrated (Milestone 5), SQL code generated by `sqlc`
  will be wrapped in a struct implementing the package's `Store` interface.
- The testing strategy is uniform: instantiate a store, create a handler,
  exercise via `httptest`. No mocking frameworks needed.
- The `Store` interface is intentionally small (2 methods in L2.2, expanding
  with FindByID/Update in L2.3). Small interfaces are idiomatic Go.
